# 实验日志

按时间倒序记录对 `chinese-poetry` 数据底座的检查、判断和后续验证。

## 2026-08-22

### 假设

- `chinese-poetry/chinese-poetry` 的核心价值可能不是权威文献研究，而是大规模诗词产品的原始语料入口。
- 相比继续制作“古诗词大全”，将真实诗词连接到现代人的情绪与生活场景，可能具有更明确的产品价值。

### 操作

- 阅读上游 README、目录结构、许可证和公开数据说明；
- 检查 `palemoky/chinese-poetry-api` 与上游数据仓库的 Submodule 关系；
- 阅读 API 项目的加载、清洗、朝代推断、体裁分类和 SQLite 建模代码；
- 查阅上游有关乱码、错漏字、重复作品、断句和作者重名的公开 Issue；
- 获取上游当前 HEAD：`b8594f81a89752241442f2ce267d6f66f96704ee`；
- 梳理学习、地域、情绪匹配、内容创作、游戏、多媒体、专业搜索和数据服务等产品方向。

### 观察

- API 项目的主要数据入口确实是 `chinese-poetry/chinese-poetry`，服务层负责格式归一、自动分类、简繁转换、存储和查询；
- 上游语料覆盖广、获取方便，但公开说明缺少大部分作品的逐条底本与采集记录；
- 历史 Issue 显示部分数据存在 OCR、乱码、缺字、错字、断句、重复和作者消歧问题；
- API 最终模型主要保留作品、作者、朝代和体裁关系，逐条来源链不足；
- 自动朝代与体裁推断适合产品检索，但不能替代文献学判断；
- 产品核心不应是数据展示，而应是“真实诗词 + AI 连接 + 现代场景 + 个人情绪体验”。

### 当前结论

- 上游不应直接作为权威研究结论的唯一依据；
- 它可以作为原始候选语料、计算实验和产品原型底座；
- 后续应建立 Raw、Normalized、Curated、Product 四层数据结构；
- 最值得优先验证的产品闭环是：用户表达处境，系统从可信语料检索少量诗句，提供出处与克制解释，并沉淀为个人文化记忆；
- 学习、地域、创作、游戏和多媒体都是扩展手段，情绪共鸣应保持为产品主线。

### 已知限制

- 本次是桌面研究，没有下载并扫描固定版本的全部 JSON；
- Issue 中记录的问题可能已有部分修复，需要针对固定 commit 重新统计；
- 尚未完成经典作品抽检、重复率测量、字符异常报告和作者冲突统计；
- 尚未进行用户访谈、情绪匹配实验或商业需求验证。
