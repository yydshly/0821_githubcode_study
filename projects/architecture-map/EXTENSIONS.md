# Architecture Map 扩展方向

Architecture Map 当前已经形成“项目代码 → 大模型理解 → 架构数据 → 交互地图 → 人工审核”的第一阶段闭环。继续扩展时，最值得投入的不是单纯增加装饰，而是同时加强下面两个系统。

## 一、地图表现能力

地图表现能力负责把抽象的软件结构转换成可以快速阅读的视觉语言。

### 当前已经实现

- 用街区表达研究治理、完成项目、实验、发布和外部世界五类领域；
- 用五种稳定颜色建立分组语义，而不是只依赖黑白轮廓；
- 用建筑高度和形态表达文件数量、代码规模与模块类型；
- 用道路表达调用、数据和支撑关系；
- 用移动载荷与步骤状态表达流程进度；
- 按等距地图的真实远近顺序绘制建筑，避免宽建筑错误覆盖前排建筑。

### 可以继续扩展

1. **视觉语法**：为 API、数据库、任务队列、文档和外部服务建立固定建筑类型。
2. **多层细节**：全景显示项目，放大后显示文件，再深入显示关键函数和调用点。
3. **版本对比**：用新增、删除和变化颜色展示两个 Git 提交之间的架构差异。
4. **风险叠层**：切换测试覆盖、循环依赖、代码增长、维护活跃度和未认领文件视图。
5. **主题和导出**：支持明暗主题、SVG/PNG、架构报告和可分享的静态快照。
6. **大型仓库性能**：聚类、按需展开和分层加载，避免一次绘制数千个节点。

表现能力的判断标准不是“像不像一座漂亮城市”，而是颜色、形状、远近和动画是否稳定表达同一种架构含义。

## 二、项目理解入口与流程驱动

项目理解能力负责回答“用户为什么要看这张地图，以及应该从哪里开始”。

### 当前已经实现

- 从项目全景进入，查看真实研究模块和发布边界；
- 从四条真实流程进入，观看研究项目如何由上游代码变成实验、结论和公开成果；
- 点击建筑查看职责、实现方式、技术栈、文件数量、代码行数和代表性源码路径；
- 通过选中、弱化和动画保持地图与说明面板同步。

### 可以继续扩展

1. **问题式入口**：提供“项目整体如何组成”“一次请求如何运行”“代码如何发布”“修改这里影响哪里”等入口。
2. **源码证据**：每个模块和关系都附带真实文件、导入语句、调用位置和生成依据。
3. **影响分析**：从一个文件或模块出发，计算上游调用者、下游依赖和可能受影响的流程。
4. **流程生成**：大模型提出候选流程，静态分析验证边，用户审核后保存为可播放路径。
5. **增量更新**：Git 提交后只重新分析变化部分，并把新旧架构差异展示给审核者。
6. **追问入口**：用户在地图中选中对象后继续询问“为什么”“由谁调用”“出错会怎样”。

项目理解能力的目标，是把一张静态全景图升级为能够带着用户阅读代码、验证结论和解释变化的导航系统。

## 两个系统如何配合

```text
用户选择一个理解问题
        ↓
大模型生成模块、关系、流程和证据
        ↓
程序校验文件、依赖与度量数据
        ↓
地图用颜色、建筑、道路和动画表达结果
        ↓
用户选择模块、查看证据并继续追问
```

地图表现能力解决“如何看懂”，理解入口与流程驱动解决“从哪里开始、接下来怎么看”。两者结合后，Architecture Map 才会从架构插图变成真正的项目理解入口。

## 推荐迭代顺序

1. 为模块和关系补充可点击的源码证据；
2. 增加“全景 / 运行流程 / 发布流程 / 影响分析”理解入口；
3. 支持 Git 版本差异和增量更新；
4. 最后再扩展更多建筑风格、主题和大型仓库渲染能力。
