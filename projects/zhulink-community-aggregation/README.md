## 结论先行

ZhuLink 不是一个可嵌入其他应用的算法库，而是一套完整的资讯社区网站。它把三个相对独立的能力连接起来：

```text
私人 RSS 阅读
      ↓ 用户主动挑选
推荐到公共社区
      ↓ 产生公开互动
公共热度与时间衰减排序
```

其核心技术均较常规，线上社区模式也尚未充分验证，因此不继续做深度复现；但“把私人信息发现转化为公共知识筛选”的产品链路有参考价值，适合在后续信息汇总、垂直资讯和非个性化社区产品中复用。

## 一、产品能力

### 1. 私人 RSS 阅读器

用户添加 RSS、Atom 或 RSSHub 地址，系统定时抓取新文章并保存标题、链接、摘要、正文和发布时间。文章首先进入订阅者自己的阅读列表，而不是自动进入公共社区。

上游实现使用 `gofeed` 解析订阅源，启动时拉取一次，此后每 30 分钟刷新；超过 30 天的 FeedItem 会在每日清理任务中删除。

### 2. 推荐到公共社区

用户可以把私人阅读器里发现的文章“移栽”成社区帖子，也可以直接发布 URL 或 Markdown 内容。

移栽时会按原文 URL 检查重复：已有帖子时为原帖自动点赞；没有帖子时创建公共 Post。用户未填写推荐语时，系统可以调用 LLM 生成摘要。

### 3. 社区互动与排序

公共帖子支持点赞、点踩、评论、收藏、浏览和管理员置顶。首页分为：

- 热门：置顶优先，再按热度分和发布时间排序；
- 最新：纯发布时间倒序；
- 节点：当前源码中按节点内发布时间倒序；
- 相关文章：使用文本向量相似度，而不是首页热度分。

### 4. AI 辅助

AI 主要用于摘要、广告或违规内容判断、SEO 元信息与文章向量，不是 RSS 信息来源，也不直接生成个性化首页。

## 二、信息进入系统的完整链路

```text
用户提交 RSS URL
        ↓
服务验证并抓取 RSS/Atom
        ↓
按 GUID 或链接去重，写入 FeedItem
        ↓
用户在私人阅读器中查看
        ↓
用户主动点击“推荐到社区”
        ↓
按原始 URL 精确检查公共帖子是否重复
        ↓
创建 Post，或给已有 Post 点赞
        ↓
其他用户投票、评论、收藏
        ↓
后台重新计算公共热度
```

如果 FeedItem 没有正文，用户打开阅读页时，服务会直接请求原网页并用 `go-readability` 提取正文；失败后再调用外部代理作为兜底。

## 三、源码中的实际排序逻辑

上游当前实际生效的互动值为：

```text
W = 点赞 × 1.0
  + 评论 × 2.0
  + 收藏 × 3.0
  + 浏览 × 0.05
  - 点踩 × 1.5
```

若 `W < 0`，先归零。随后计算：

```text
Score = 1000 × log10(W + 1) / (发布小时数 + 24)^1.5
```

计算结果被转换成整数后写入 `posts.score`。热门首页查询为：

```sql
ORDER BY is_top DESC, score DESC, created_at DESC
```

因此这里所谓“去算法”，准确含义是“不做基于个人画像的千人千面推荐”，而不是取消排序算法。所有用户共享同一套公共热度规则。

README 和 `story.go` 中还保留 Hacker News 风格的 `(P-1)/(T+2)^G` 描述及未调用函数，但当前首页实际依赖的是 `utils.CalculateScore` 生成的持久化分数。

## 四、线上验证与发现

在 `2026-08-21` 对线上实例进行只读检查：

- “热门”页前两篇非置顶文章显示热度 `1`；
- 随后可见文章多数显示热度 `0`；
- “最新”页与“热门”页去掉置顶项后的顺序基本一致；
- 页面表现与 `score DESC, created_at DESC` 的源码逻辑能够相互解释。

原因是衰减结果被转换为整数。低互动站点中，大量文章很快从 `0.x` 截断为 `0`，此时热门页的最终排序只能依赖 `created_at DESC`，表现为“热门退化成最新”。

这不是算法没有运行，而是算法对低互动密度不适配。

## 五、参考价值

### 值得保留的产品思路

1. **用户控制信息源**：平台不替用户决定全部阅读来源，私人订阅列表保持可控。
2. **私人发现连接公共讨论**：推荐动作把“我读到什么”转化为“为什么大家值得读”。
3. **公共排序可解释**：热门、最新、人工精选可以明确分开，避免黑盒个性化信息流。
4. **RSS 解决候选供给**：社区不必完全依赖用户手工发现链接，RSS 提供持续候选池。
5. **AI 作为辅助层**：摘要、标签、去重和垃圾检测可提高处理效率，但不应取代用户判断。

### 不应直接照搬的实现

1. 不要把衰减后的浮点排名直接转成整数保存。
2. 不要期待低流量社区仅靠投票公式自然产生高质量首页。
3. 不宜把普通浏览量直接作为重要质量信号，浏览量容易被刷新和机器人放大。
4. 评论数量可能代表争议而非质量，应使用对数、平方根或上限压缩。
5. 人工置顶、编辑精选和算法热门必须分开标注，不能暗中混入一个分数。
6. RSS 抓取必须补充 SSRF 防护、内网地址拦截、重定向检查、按域名限速和条件请求。
7. URL 去重应做规范化，移除 `utm_*`、`fbclid` 等跟踪参数，并保留来源映射。
8. 社区排序必须与举报、反作弊、重复内容和站点集中度治理一起设计。

## 六、类似产品的推荐实现方式

### 第一阶段：先验证私人价值

- RSS/Atom 订阅；
- 定时抓取与去重；
- 私人阅读、分类和已读状态；
- 不建设复杂社区和 AI 能力。

### 第二阶段：建立公共推荐桥梁

- 一键推荐 FeedItem；
- 要求用户写一句“为什么值得读”；
- URL 规范化和公共帖子去重；
- 最新、人工精选两个明确列表。

### 第三阶段：引入社区共识

- 点赞、评论、收藏和举报；
- 使用浮点热度，不覆盖原始互动计数；
- 新帖最低曝光或独立探索队列；
- 热门、最新、精选保持独立入口。

### 第四阶段：流量起来后再优化

- 反作弊与投票环检测；
- 来源多样性和同域名降噪；
- 排名公式版本化和可回放；
- AI 摘要、主题标签、内容去重和相似文章。

## 七、推荐的数据与排名原则

数据库应永久保留原始事件，而不是只保留最终排名：

```text
votes
comments
bookmarks
flags
impressions
posts.created_at
```

排名值使用 `DOUBLE PRECISION` 或 `NUMERIC`，按互动事件异步刷新并定期重算。第一版可以使用简单、可解释且不归零的先验：

```text
质量值 = 点赞
       + 1.5 × sqrt(评论数)
       + 2.0 × sqrt(收藏数)
       - 3.0 × 举报数

HotScore = (质量值 + 2)^0.8 / (发布小时数 + 2)^1.3
```

具体权重不是结论，应根据真实数据调整。更重要的原则是：不截断浮点排名、保留原始计数、记录公式版本，并让人工干预可见。

## 八、后续产品决策清单

开发类似产品前，先回答：

- 产品首先是私人阅读工具，还是公共链接社区？
- 谁负责冷启动内容供应？
- 用户为什么愿意从私人阅读器推荐到公共社区？
- 推荐理由是否比单纯转发链接更重要？
- 热门、最新和人工精选是否清晰区分？
- 新帖子如何获得最低曝光？
- 如何防止单一账号或单一网站占据内容供给？
- 排名公式能否通过历史事件回放验证？
- AI 的判断是否可见、可申诉、可关闭？

## 九、最终评价

ZhuLink 的研究价值有限：核心技术栈和算法均属于常见 Web、RSS 与社区实现，线上数据暂不足以证明其社区筛选模型有效。

它的参考价值主要在产品组合：

> RSS 负责持续发现候选信息，用户负责把私人发现推荐到公共空间，社区负责公开评价，排序系统负责组织注意力。

未来开发信息汇总社区时，可以复用这条链路，但应重新设计冷启动、排序精度、反作弊、来源多样性和人工编辑机制。
