## 一、项目能力、细节与关键点

### 1.1 准确定位

该项目是本地“电子书到有声书”生产框架，不是自研 TTS、OCR 或文档理解算法。它把成熟组件组织为可恢复的批处理流水线：

```text
文件/文本输入
  → 格式识别与预处理
  → EPUB/XHTML 统一层
  → 正文提取、清洗、分块和分句
  → 可选翻译与人工预览
  → TTSManager 选择一个本地 TTS 后端
  → 逐句生成 FLAC
  → FFmpeg 合并并输出 M4B/MP3 等格式
```

### 1.2 能力范围

| 能力层 | 实现内容 | 主要依赖 |
| --- | --- | --- |
| 输入 | 文件上传、文本框、单本和批量转换 | Python/Gradio/CLI |
| 格式兼容 | EPUB、MOBI、AZW、FB2、PDF、DOCX、PPTX、图片等 | Calibre `ebook-convert` |
| 文本提取 | EPUB spine、XHTML正文、元数据、目录、封面 | EbookLib、BeautifulSoup |
| OCR | 扫描 PDF、图片、纯图片 PPTX/DOCX | PyMuPDF、Pillow、Tesseract |
| 文本处理 | 非正文过滤、日期数字转读法、标点和停顿、语言分句 | 规则、Stanza、num2words |
| 翻译 | 按 block 本地翻译并保护 SML 标签 | Argos Translate |
| 语音 | 多个本地开源 TTS、参考音色、部分声音转换 | XTTS/Bark/Piper/VITS/MMS 等 |
| 生产 | 缓存、失败重试、断点恢复、逐句文件、音频合并 | JSON、SQLite、FFmpeg |
| 编辑 | block 预览、保留/删除、逐块声音和引擎字段 | 内置界面和中间数据 |

### 1.3 统一中间数据

项目先把来源尽量规范为 EPUB，再把 EPUB spine 中每个 XHTML 文档转为一个 block。block 包含稳定 ID、正文、是否保留、声音、TTS 引擎、微调模型和句子列表。需要注意：这里的 block 只是 EPUB 文档单元，不保证等于真实章节。

```json
{
  "id": "uuid",
  "keep": true,
  "text": "适合朗读的正文",
  "voice": "voice.wav",
  "tts_engine": "XTTS",
  "fine_tuned": "internal",
  "sentences": []
}
```

原始 block 和已保存编辑版本使用 JSON，当前转换状态使用 SQLite；输入校验和、block 哈希和句子文件共同支持重跑、对齐和断点续传。

### 1.4 真实优势与边界

优势：

- 可完全离线，避免按字数调用云端 TTS；
- 格式覆盖广，能够批量生成完整音频文件；
- 模型、声音、设备、缓存和封装已形成统一生产流程；
- 对失败重试、断点恢复和人工预览考虑较完整；
- MMS/Fairseq 提供低资源语言的长尾覆盖。

边界：

- 没有自研基础模型，最终语音质量取决于所选开源 TTS；
- 默认不具备 LLM 级章节理解、人物识别、情绪导演和全书一致性；
- 复杂 PDF、表格、脚注和图文关系仍是规则解析；
- “支持 1000+ 语言”主要来自大量单语言 MMS/VITS 模型，不代表质量一致；
- 本地模型需要下载权重、安装复杂依赖并消耗显存、内存和生成时间；
- 当前价值主要是工程集成，不构成必须整体引入的技术壁垒。

## 二、格式转换技术

### 2.1 支持范围与统一路线

源码配置声明支持：

```text
.epub .mobi .azw3 .fb2 .lrf .rb .snb .tcr .pdf
.txt .rtf .doc .docx .html .odt .azw .tiff .tif
.png .jpg .jpeg .bmp .pptx .zip
```

核心设计不是为每种格式维护完整解析器，而是先进行必要的专用预处理，再统一调用 Calibre 输出内部 EPUB：

| 来源 | 处理方式 | 主要风险 |
| --- | --- | --- |
| EPUB/MOBI/AZW/FB2/RTF/ODT/HTML | 直接交给 Calibre 规范化为 EPUB | 原格式的复杂样式、脚注和结构可能损失 |
| TXT | 规范换行，把连续空行转成暂停，再交给 Calibre | 缺少章节和语义结构 |
| PDF | PyMuPDF逐页检查；有文本则提取XHTML，无文本则300 DPI渲染后OCR | 双栏顺序、页眉页脚、隐藏错误文字层 |
| DOCX | 有可提取文本时由Calibre处理；完全无文字时提取内嵌图片OCR | 文本框、浮动元素、批注和混合图文 |
| PPTX | 提取文本框、段落和表格；纯图片页执行OCR，再生成XHTML | shape顺序不等于视觉阅读顺序 |
| PNG/JPG/TIFF/BMP | Pillow读取单帧或多帧，Tesseract OCR后生成XHTML | 分辨率、倾斜、表格和复杂版面 |
| ZIP | 识别单个嵌套EPUB或EPUB根目录并重新封装 | 不是通用多书压缩包导入 |

### 2.2 EPUB正文提取

转换完成后，EbookLib按照 spine 确定文档级阅读顺序，读取元数据、封面和 XHTML。BeautifulSoup删除脚本与样式，识别标题、段落、换行、容器和表格：

- `h1`～`h4`作为标题并追加停顿；
- `p`、`br`、`span`转为文本和短停顿；
- `div`产生较明显停顿；
- 表格按“表头：单元格”线性化；
- 根据 `epub:type`排除目录、版权页、索引、附录等非正文类型。

排除规则适合小说批处理，但可能误删用户需要的前言、后记、附录或参考文献。

### 2.3 OCR与清洗

Tesseract通过`image_to_data`返回文本块，项目按`block_num`组合内容，以标点、大小写和长度规则合并断行，并用全大写或短标题等规则猜测标题。缺少语言数据时会尝试下载对应`tessdata_best`模型。

清洗阶段会：

- 删除代码块、行内代码、URL、文件路径、LaTeX、部分方程式和Emoji；
- 保留可发音数学符号，再按语言转换读法；
- 转换日期、年份、时间、普通数字、罗马数字和缩写；
- 归一化换行、空格、引号、重复标点和特殊字符；
- 为中日韩等无空格语言使用专门的分句处理；
- 根据目标 TTS 最大字符数拆分长句，并合并过短句子。

这是“面向可朗读性”的有损清洗。小说通常受益，数学、代码、教材和技术文档可能丢失关键信息。

### 2.4 质量保障现状

项目使用扩展名、空文件、Calibre退出码、EPUB输出、正文为空、OCR为空、校验和、block哈希、失败中止和人工预览来降低错误，但没有完整性和准确性证明：

- 没有源文档与目标文本的字符/段落覆盖率对比；
- 没有使用OCR置信度触发二次识别；
- 没有复杂版面阅读顺序模型；
- 没有低置信度页面审核队列；
- 没有用ASR把生成音频反识别后与目标文本对齐。

因此它能保证流程可运行和结果可恢复，不能保证任意来源都逐字忠实。常见、结构规范的小说 EPUB 不构成技术难点；任意复杂文档的商业级质量属于成本、验证和长尾覆盖问题，而非单一模型选型即可完全消除。

## 三、TTS选择与能力

### 3.1 TTSManager的角色

`TTSManager`只是统一工厂和适配层：读取当前任务的`tts_engine`，从注册表创建一个后端实例，再把声音设置和逐句转换调用转发给具体引擎。一次任务通常选择一个主引擎，不是每句话自动智能选择模型。

### 3.2 引擎能力矩阵

| 引擎 | 生成/克隆路径 | 适合场景 | 主要限制 |
| --- | --- | --- | --- |
| XTTS v2 | 文本+参考音频直接条件生成，原生零样本克隆 | 中英日韩等主要语言、需要参考音色的通用本地方案 | 较慢，长文本可能重复或发音漂移，语言约17种 |
| Bark | 生成式音频和说话人提示 | 短对白、语气和非语言声音实验 | 不稳定、可能幻觉或重复、资源需求高 |
| Tortoise | 英语参考音频条件生成 | 少量高质感英语片段 | 英语限定且非常慢，不适合整本批量 |
| Piper | ONNX固定声音快速生成；指定音色时再接KNNVC | CPU、低资源、离线批量朗读 | 表达力较弱，声音转换不等于原生克隆 |
| VITS | 单语言/说话人端到端TTS；可接KNNVC | 稳定、快速、多语言模型资源 | 情绪和零样本能力依模型而定 |
| Fairseq/MMS | 按语言加载Meta MMS单语言VITS；可接KNNVC | 1000+低资源语言和方言覆盖 | 不是一个统一多语言模型，质量和音色数量不一致 |
| GlowTTS | 快速对齐稳定的基础TTS；可接KNNVC | 资源较低、稳定朗读 | 自然度和表现力一般 |
| Tacotron2 | 经典自回归TTS；可接KNNVC | 使用已有成熟模型 | 长句可能漏字、重复或对齐失败 |
| YourTTS | 文本+参考音频原生零样本克隆 | 英语、法语、葡萄牙语的轻量克隆 | 技术较旧，综合能力通常弱于XTTS v2 |

### 3.3 两种“声音克隆”不能混淆

原生条件生成：

```text
文本 + 参考声音 → 直接生成目标说话人的语音
```

典型为 XTTS、YourTTS、Tortoise，Bark也有自己的参考声音机制。音色条件参与生成过程，但仍不等于自动理解人物情绪。

后期声音转换：

```text
文本 → Piper/VITS/MMS等基础音色 → KNNVC → 接近目标音色
```

后者主要改变音色，基础TTS已经确定的节奏、停顿、重音和表演通常不会被根本改善。

### 3.4 我们的选择建议

| 需求 | 首选路线 |
| --- | --- |
| 中文自然度、角色和情绪导演 | LLM生成结构化朗读脚本 + MiniMax TTS |
| 完全离线且需要参考音色 | XTTS v2，先做小规模音质和稳定性验证 |
| CPU低成本批量生成 | Piper |
| 低资源语言覆盖 | MMS/Fairseq，逐语言验收，不以“1000+”替代质量测试 |
| 实验性、表现力短片段 | Bark |
| 少量英语高质感片段 | Tortoise |

选择标准应包括语言、音质、情绪控制、声音一致性、速度、硬件、许可证、部署成本和是否允许云端处理，而不是只比较模型名称。

## 四、后续扩展与我们的路线

### 4.1 当前决策

不安装完整项目，原因如下：

- 现阶段没有离线整本有声书的明确交付需求；
- 已有“LLM + MiniMax TTS”能力更贴合中文内容理解和表达；
- 完整安装会引入多个大模型、系统工具和设备兼容成本；
- 项目的关键设计可以按模块参考，不需要接受其全部依赖和内部数据结构。

### 4.2 推荐的自有架构

未来需要二次开发时，建议把“统一转EPUB”升级为保留来源证据的统一文档模型：

```text
EpubAdapter / PdfAdapter / DocxAdapter / PptxAdapter / ImageAdapter
                              ↓
                         Document IR
       metadata / sections / blocks / page / bbox / confidence
                              ↓
                  规则清洗 + LLM受控语义处理
         章节、角色、对白、情绪、停顿、读法和声音规划
                              ↓
                    Provider-neutral TTS API
                 MiniMax / XTTS / Piper / 其他服务
                              ↓
                    音频拼接、ASR回验和导出
```

`Document IR`至少保存：

```json
{
  "source": {"type": "pdf", "page": 12},
  "type": "paragraph",
  "text": "原始提取文本",
  "normalizedText": "朗读文本",
  "bbox": [72, 110, 530, 210],
  "confidence": 0.96,
  "speaker": "narrator",
  "emotion": "neutral",
  "changes": []
}
```

这样可以保留原文、位置、清洗结果和LLM修改记录，支持回溯，而不是在早期扁平化后永久丢失版面信息。

### 4.3 按需复用清单

未来可以直接参考的设计：

- 多格式Adapter和失败回退到OCR的路由；
- block稳定ID、缓存、哈希、断点续传和源文件变更后的对齐；
- SML中的暂停、换声等运行时标记；
- 逐句中间音频和最终FFmpeg封装；
- 本地TTS注册表与统一Provider接口；
- 声音样本的VAD、降噪、去背景和响度归一化。

建议重新设计的部分：

- 不把EPUB作为唯一内部真相，使用可追溯Document IR；
- OCR引入置信度、版面分析、多引擎回退和低分页面队列；
- LLM只做受控修改，保存`source/corrected/changes/confidence`；
- TTS统一成云端和本地都可插拔的Provider接口；
- 使用ASR回验发现漏读、重复和幻觉；
- 按章节维持人物、发音词典和声音的一致状态；
- 为版权、DRM、模型、声音克隆和内容来源分别建立授权记录。

### 4.4 触发重新评估的条件

满足任一条件时再打开本归档：

1. 需要完全离线或隐私敏感的整本有声书生产；
2. 云端TTS成本成为批量业务的主要瓶颈；
3. 需要MiniMax不覆盖的低资源语言；
4. 需要M4B章节、封面、元数据和长音频恢复能力；
5. 需要用户自带模型或私有化声音克隆；
6. 出现大量PDF、扫描件、DOCX、PPTX统一入库需求。

届时应先抽取最小模块做基准，不直接安装全部引擎：用真实样本比较文本覆盖率、OCR错误率、角色准确率、TTS漏读率、实时系数、显存和单小时成本，再决定复用代码、重写适配器或只调用单个模型。

## 总结

ebook2audiobook已经证明“多格式文档 + 本地开源TTS + 有声书生产”不存在基础技术阻塞。其竞争力来自工程覆盖而非独占算法。当前最合理决策是归档而不安装：保留格式路由、block生产、TTS注册和断点封装等设计；未来围绕我们的LLM语义导演和MiniMax TTS路线，按明确需求吸收单个模块，并补上可追溯Document IR、质量评分和音频回验闭环。
