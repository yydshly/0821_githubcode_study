# 从机械场景到故事与产品

当前主入口是 [`showcase/`](showcase/)。它不是把 fleet lab 换一套 UI，而是把用户的理解路径拆成三个职责不同、证据连续的阶段。

## 三个入口分别证明什么

| 入口 | 用户看到什么 | 它证明什么 | 实现方式 |
| --- | --- | --- | --- |
| 01 原作演示 | 11 个原始模型、deploy/retract/destroy、时间轴、爆炸视图、审计 | 上游真实能力，不是研究页面的模拟 | iframe 直接运行固定子模块的 `upstream/index.html` |
| 02 技术解剖 | watchtower 七个部署步骤、目标零件、通道、包围框、扩展接口 | 效果来自零件层级与声明式状态，不是预录视频 | `rig.setTime('deploy', t)` + `BoxHelper` + 相机导演 |
| 03 产品故事 | 空场、侦察、通路、防线、响应、全景六章 | 多个模型可以组成因果明确的产品体验 | 五个 Rig + chapter director + clip schedule + camera presets |

这条路径的顺序不能反过来：如果先讲宏大故事，却没有原作和技术证据，故事会像包装；如果只留下原作和参数，用户又只能看到一组技术玩具。

## 技术效果的真实实现链

```text
模型 Factory
  ↓ 创建
THREE.Group / Mesh 零件层级
  ↓ 登记
parts: name + group + object + explode
  ↓ 描述
clips: sequence(at, duration, channels, appear, sound)
  ↓ 编译
createRig() 按零件和 transform channel 建立轨道
  ↓ 每帧
update(dt) → ease → position/rotation/scale/visible
  ↓
WebGLRenderer 把 Object3D 场景提交给 GPU
```

其中最重要的不是 Three.js 几何体，而是三类约束：

1. **结构约束**：门板的父节点 pivot 必须位于铰链；子零件跟随父级运动。
2. **时间约束**：底层先支撑，上层再出现；收回顺序相反；声音必须绑定真实运动。
3. **验收约束**：零件出现时必须被地面或父体遮蔽，静止态不能共面、埋藏或悬空。

技术解剖页的七个步骤对应真实 watchtower 时间：地缝、盖板、底座、立柱、塔头、翼板和锁扣。页面通过 `setTime()` 直接读取上游 Rig 姿态，没有重写一套假动画。

## 为什么 fleet lab 只是一个场景

一个场景通常只有以下内容：

```text
若干模型 + 一套灯光 + 一个相机 + 一组操作按钮
```

它能回答“同时放 25 个模型会怎样”，却不能回答：

- 为什么这些设施在这里？
- 哪个先出现，为什么？
- 用户在等待什么结果？
- 状态变化与产品价值有什么关系？
- 最后应该记住什么？

故事需要增加**因果、节拍和结果**；产品还需要增加**目标用户、问题、操作与证据**。

## 场景、故事、产品的四级扩展

### Level 1：对象场景

把模型放到空间中，提供相机和基础交互。fleet lab 属于这一层。

### Level 2：情境场景

加入地点、时间和威胁，例如“极夜荒原中的地下前哨”。环境不只是背景，而是解释为什么需要部署。

### Level 3：故事体验

定义不可交换的节拍：

```text
空场
  ↓ 没有观测能力
侦察上线
  ↓ 看见目标但无法到达
通路恢复
  ↓ 有连接但没有防御
防线升起
  ↓ 威胁进入射界
告警响应
  ↓
前哨在线
```

每章都必须同时改变三件事：3D 状态、可读文案、产品结果。只移动镜头不算故事推进。

### Level 4：真实产品

在故事之上增加可操作闭环：

- 建造选址与资源成本；
- 部署倒计时和中断风险；
- 侦察覆盖、防御半径与通路状态；
- 模块损伤、升级与回收；
- 权威状态、存档和多人同步；
- 任务结果、报告或下一步行动。

当前 showcase 验证到 Level 3，是产品叙事原型，不宣称已经实现 Level 4 的游戏规则和后端。

## “极夜前哨”的产品映射

| 故事章 | 3D 变化 | 产品含义 | 可继续扩展的玩法 |
| --- | --- | --- | --- |
| 待命 | 所有 Rig 在地下 | 隐藏且不干扰环境 | 选址、资源准备、隐蔽值 |
| 侦察 | dish 部署 | 建立信息覆盖 | 扫描范围、目标发现、通信质量 |
| 通路 | bridge 部署 | 恢复空间连接 | NavMesh、运输效率、载重 |
| 防线 | tower + sentries 错峰部署 | 建立防御网络 | 建造窗口、射界、能源分配 |
| 响应 | sentry 播放 alert clip | 状态变化变成明确反馈 | 目标锁定、攻击授权、误报处理 |
| 在线 | 镜头回到系统全景 | 模型组成完整服务 | 前哨健康度、任务完成、扩建入口 |

## 导演系统如何扩展

当前 chapter director 维护：

```js
{
  title,
  description,
  outcome,
  hold,
  camera,
  target
}
```

进入章节时，导演先恢复确定性 baseline，再调度指定 Rig 的 clip。这样手动跳章、自动播放和重置不会依赖之前偶然播放到哪里。

下一步可以增加：

- chapter marker 与字幕/旁白时间；
- 环境光、天气、粒子和音景轨道；
- 分镜曲线而非单一 camera preset；
- 事件条件，让故事由玩家操作而非固定时间推进；
- 产品数据绑定，使覆盖范围、风险和完成度来自真实状态；
- Film Mode 录制、字幕和发布包。

## 从现有代码继续添加内容

### 添加技术步骤

在 `showcase/showcase.mjs` 的 `techSteps` 中添加真实 clip 时间、零件名、transform 通道、相机与扩展说明。零件必须来自 `rig.parts`，时间必须来自真实 deploy clip。

### 添加故事设施

在 `storySpecs` 中登记 factory 和世界位置，再在 `setStoryBaseline()` 与章节调度中定义它何时处于地下、部署完成或播放其他 clip。

### 添加故事章节

为 `storyChapters` 增加标题、结果、时长和相机，同时在 `enterStoryChapter()` 中调度动作。验收时必须检查自动播放、直接跳章和 reset 三条路径。

## 生产化时需要替换什么

| 当前原型 | 真正产品方向 |
| --- | --- |
| 程序化低模 | Blender/GLB 分件资产与节点规范 |
| 固定章节数组 | 任务/状态机驱动的导演数据 |
| 固定相机 preset | 分镜曲线、碰撞避免与玩家接管 |
| 每实例独立资源 | Geometry/Material 缓存、合并、Instancing、LOD |
| 浏览器本地状态 | snapshot、startedAt、seed、网络权威状态 |
| 关键帧坍塌 | 关键帧到物理刚体的受控切换 |

核心原则是保留上游最有价值的 `parts + clips + audits` 语法，把资产、规模、玩法和导演系统放在它周围，而不是把所有职责塞回单个模型文件。
